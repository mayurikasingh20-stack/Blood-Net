1. PROJECT OVERVIEW
================================================================================

Blood Net is a full-stack blood donation management web application that connects
four kinds of users on one platform:

  - DONORS      -> donate blood to people in need
  - PATIENTS    -> raise blood requests when they need blood
  - BLOOD BANKS -> manage their blood inventory and fulfill requests
  - ADMINS      -> approve blood banks, verify donations, block users, manage everything

The project has two independent parts that talk to each other over HTTP:

  - BACKEND  (Python + Flask)  -> /Backend
      * REST API, all business logic, database, authentication, notifications.
  - FRONTEND (React + Vite)    -> /frontend
      * Single Page Application (SPA). Dashboards, forms, maps, UI.

  - DATABASE: SQLite (file-based, no server installation required).
      * Stores data in /Backend/instance/bloodnet.db (auto-created on first run).

WHAT IT SOLVES
  - Hospitals/patients struggle to find matching blood quickly in emergencies.
  - Blood banks can't easily track stock (inventory) per blood group.
  - This platform broadcasts urgent requests to the RIGHT donors in the RIGHT
    city with the RIGHT blood group automatically.

2.1 BACKEND - EVERY SINGLE LIBRARY
------------------------------------------------------------------------------

DIRECT DEPENDENCIES (from Backend/requirements.txt):

  - Flask >=3.1,<4
      The core web framework. WHY: Lightweight, minimal boilerplate, perfect for
      building a REST API. We use the "application factory" pattern
      (app/__init__.py create_app()) and Blueprints to split routes by feature
      (auth, admin, donor, patient, blood_bank, etc.).

  - Flask-SQLAlchemy >=3.1,<4
      ORM (Object Relational Mapper). WHY: Lets us define database tables as
      Python classes and query them with Python instead of writing raw SQL.
      Prevents SQL injection, gives us relationships between tables
      (one-to-one, one-to-many), and auto-creates tables with db.create_all().

  - Flask-JWT-Extended >=4.7,<5
      JWT (JSON Web Token) authentication. WHY: Instead of server-side sessions
      (Flask-Login), we issue a signed token on login. The token is sent in the
      Authorization header and verified on every protected route. This makes the
      API stateless and easy to scale. Provides:
        * create_access_token / create_refresh_token
        * @jwt_required() route guard
        * get_jwt_identity() to know the current user
        * Custom handlers for expired / invalid / missing tokens.
      NOTE: We do NOT use Flask-Login. All authentication is token-based.

  - Flask-Cors >=6,<7
      CORS (Cross-Origin Resource Sharing). WHY: The React frontend runs on
      http://localhost:5173 but the API runs on http://127.0.0.1:5000. Without
      CORS the browser blocks the requests. We whitelist only localhost:5173.

  - Flask-Migrate >=4,<5
      Database migrations (built on Alembic). WHY: Tracks schema changes over
      time so we can upgrade the database without deleting data. (Declared in
      requirements; the app uses db.create_all() + a few ALTER TABLE safety
      checks on startup.)

  - python-dotenv >=1,<2
      WHY: Loads configuration from Backend/.env (SECRET_KEY, JWT_SECRET_KEY,
      DATABASE_URL, Twilio credentials) so secrets are never hard-coded.

  - requests >=2.32,<3
      HTTP client for the backend. WHY: Used to call external services -
      specifically the OpenStreetMap Nominatim API for geocoding addresses
      into latitude/longitude (app/services/geocoding_service.py).

  - twilio >=9,<10
      Twilio SDK. WHY: Sends and verifies one-time passwords (OTPs) via SMS
      through Twilio Verify (app/services/twilio_service.py). Used for:
        * Phone verification during registration
        * Password reset flow
      The real OTP verification happens on Twilio's servers; we only start a
      verification and then check its status.

INDIRECT / TRANSITIVE PYTHON PACKAGES (installed automatically with the above):

  - SQLAlchemy >=2.x
      The actual ORM engine behind Flask-SQLAlchemy. We use it directly in
      services for advanced queries: func (SUM/COUNT/COALESCE), or_ , case(),
      join(), ilike(). Examples: admin_dashboard() counts, patient_dashboard()
      sums units, get_top_requests() orders by urgency.
  - Werkzeug
      Sits under Flask. We use it directly:
        * werkzeug.security.generate_password_hash / check_password_hash
          (app/utils/password.py) -> hashes passwords (PBKDF2) so plain-text
          passwords are never stored.
        * werkzeug.utils.secure_filename (app/utils/file_upload.py) -> cleans
          uploaded filenames before saving.
        * werkzeug.exceptions.HTTPException -> used by global error handlers.
  - Alembic
      Migration engine used by Flask-Migrate.
  - Jinja2
      Flask's template engine (dependency; we return JSON, not HTML templates).
  - ItsDangerous
      Used by Flask internally for secure signing (e.g. sessions/signatures).
  - Click, MarkupSafe, Blinker, colorama, etc.
      Standard parts of the Flask dependency chain.

PYTHON STANDARD LIBRARY MODULES WE USE:

  - os                     -> file paths, env variables, upload folders
  - re                     -> regex (email/phone validation, validators.py)
  - datetime / date        -> date math (56-day donation interval, expiry checks)
  - functools.wraps        -> custom decorators (utils/decorator.py)
  - random                 -> random selection (public blood bank "random" API)
  - uuid                   -> unique filenames for uploaded files
  - enum                   -> status enums in models (RequestStatus, etc.)
  - traceback              -> printing full errors in global error handlers
  - importlib / sqlalchemy -> used inside create_app for schema checks

2.3 WHY THESE OVER OTHER OPTIONS (quick justification)
------------------------------------------------------------------------------
  - Flask instead of Django: much lighter, only what we need for a JSON API.
  - Flask-Login NOT used: we chose stateless JWT tokens so the same token works
    across multiple browser tabs and mobile clients; no server-side session
    store needed.
  - SQLite instead of PostgreSQL/MySQL: zero setup for a demo/college project,
    fully portable (single file). Can be swapped by changing DATABASE_URL.
  - React instead of Vue/Angular: huge ecosystem, easy component reuse.
  - Vite instead of CRA: much faster dev/build experience.
  - Tailwind instead of Bootstrap/MUI: full design control, no pre-built
    component look, keeps bundle small (only used utilities are generated).
  - Axios instead of fetch: built-in interceptors and error handling that
    fetch() lacks.

4. USER ROLES & THEIR CAPABILITIES

e.g. "donor,patient" (dual-role) or "admin". Registration as a normal user
always creates BOTH a donor and a patient profile ("donor,patient"); role data
is stored in the profile tables (donors / patients).

Important rules enforced by the backend:
  - A rejected blood bank cannot log in at all (login is blocked).
  - A blocked user cannot use any protected API (checked in @role_required).
  - Admins cannot be blocked.
  - Donors must pass screening AND wait 56 days before accepting a request.

5. ALL FEATURES & HOW THEY WORK
================================================================================

------------------------------------------------------------------------------
5.1 AUTHENTICATION SYSTEM (JWT, no Flask-Login)
------------------------------------------------------------------------------
  * Registration: password hashed with Werkzeug (PBKDF2). Never stored in
    plain text. Email and phone must be unique.
  * Phone verification: user requests OTP (/api/auth/send-otp) -> Twilio Verify
    sends SMS. User submits code (/api/auth/verify-otp) -> phone is marked
    "verified" in a temporary server set. On successful registration, the user's
    phone_verified flag is set to true. Login is refused until the phone is
    verified.
  * Login: user enters email OR phone + password. If valid, the server issues:
      - access_token  (expires in 30 minutes)
      - refresh_token (expires in 30 days)
  * Protected routes use @jwt_required(); the frontend sends the token in the
    Authorization: Bearer <token> header.
  * Token refresh: when the access token expires (HTTP 401), the frontend
    automatically calls /api/auth/refresh with the refresh token to get a new
    access token and retries the original request. Concurrent 401s are queued.
  * Change password: requires the current password (verified against hash).
  * Forgot/reset password: OTP to phone + matching phone on account +
    verified-phone requirement, then new password is hashed and saved.
  * Delete account: removes user + all related rows (donations, requests,
    camps, notifications, profiles) in a single transaction.
  * Add role: a donor can add the "patient" role and vice versa
    (used for dual-role accounts) - creates the missing profile row.
  * Multi-tab support: each browser tab keeps its own token via sessionStorage
    (per-tab) + an in-memory variable; localStorage is only a fallback for
    "remember me". Logging out in one tab clears storage; storage events keep
    tabs in sync.

------------------------------------------------------------------------------
5.2 BLOOD REQUEST SYSTEM (core flow)
------------------------------------------------------------------------------
  Who can create: patient (auto creates a Patient profile if missing) and an
  approved blood bank.

  Validation (server-side): blood group must be valid, units > 0, hospital and
  address required, required_before cannot be in the past, urgency must be one
  of Low/Moderate/High/Critical.

  On successful creation, the backend automatically broadcasts notifications:
    a) to every matching donor (same blood group, available, eligible, SAME city),
    b) to every approved blood bank,
    c) to every admin.

  Statuses of a request: pending -> (completed | cancelled).
  The frontend displays "Responded" (teal) when accepted_count > 0 even though
  the DB status stays pending, so patients see donor responses clearly.

  Other request features:
    - List my requests (owner) / open requests (everyone except already-accepted
      for donors) / single request / accepted donors of a request.
    - Update request (owner only, not allowed after completed/cancelled).
    - Cancel request (owner only; completed cannot be cancelled).
    - Get matching donors (same group + same city + available + eligible).
    - Top 7 public requests endpoint (no auth) for the landing page, ordered by
      urgency then newest.

------------------------------------------------------------------------------
5.3 DONOR ELIGIBILITY SCREENING
------------------------------------------------------------------------------
  WHY: to prevent medically unsafe donations and to enforce a real donation
  cycle. Backend enforces screening even if the frontend is bypassed.

  Three gates must ALL pass before a donor can accept a request:
    1) Blood group match with the request.
    2) 56-day interval since last donation (Donor.check_donation_interval()).
       The API returns the next eligible date if failed.
    3) 10-question Yes/No health questionnaire (screening_service.py):
       e.g. healthy today? fever in last 14 days? on antibiotics? alcohol in
       24h? tattoo in 6 months? surgery in 6 months? serious illness? donated
       in last 56 days? doctor ever advised against? willing today?
       Each question has an expected answer; wrong answers are collected and
       returned as failed_reasons and stored on the donor row.

  The donor model stores: screening_completed, screening_date,
  screening_result (passed/failed), failed_reason.

  Flow in UI: Donor clicks "Accept" -> DonorScreeningModal shows questions ->
  answers submitted -> if passed, the accept request is sent. The accept API
  also re-checks screening + interval server-side.

------------------------------------------------------------------------------
5.4 DONATION SYSTEM (accept -> verify)
------------------------------------------------------------------------------
  Donor accept (POST /api/donations/accept/<request_id>):
    - Requires donor profile, available=true, screening passed, 56-day interval,
      request still pending, request not created by self, no duplicate response.
    - Creates a Donation row (status = ACCEPTED) and notifies the patient.

  Blood bank accept (POST /api/blood-bank/accept-request/<request_id>):
    - Same checks but for an approved blood bank; notifies the patient.

  Fulfill from inventory (POST /api/blood-bank/fulfill-request/<request_id>):
    - Bank must be approved, request pending, request not self-created.
    - Requires enough stock of the request's blood group; deducts units,
      recomputes stock status, marks request COMPLETED with fulfilled_units =
      requested units, notifies the patient.

  Patient verifies a donation (POST /api/donations/<donation_id>/fulfill):
    - Only the request owner can do it, donation must be in ACCEPTED state.
    - donated_units must be > 0 and not exceed remaining needed units.
    - Marks donation VERIFIED, sets donor.last_donation_date = today, increases
      fulfilled_units, auto-completes the request if fulfilled_units >= units,
      notifies the donor.

  Patient marks whole request fulfilled / not fulfilled
  (PATCH /api/blood-request/<id>/patient-update):
    - 'fulfilled': completes request, verifies all accepted donations
      (donated_units = 1 each), updates donors' last_donation_date, notifies.
    - 'not_fulfilled': cancels all accepted donations, keeps request open,
      notifies donors.

  Admin verify / reject donation:
    - verify: donation -> VERIFIED, fulfilled_units += donated_units, adds
      donated units to the bank's inventory (creates the inventory record if
      missing), completes the request when full, notifies donor.
    - reject: donation -> REJECTED with a reason, notifies donor.

  Donor cancel / patient remove response:
    - Donor can cancel their own ACCEPTED donation (not if VERIFIED).
    - Patient can remove an accepted response (donation -> CANCELLED) and the
      responder is notified.

------------------------------------------------------------------------------
5.5 INVENTORY SYSTEM
------------------------------------------------------------------------------
  * One Inventory row per blood group per blood bank (unique constraint
    uq_blood_bank_blood_group).
  * Add units: if a row for that group exists, units are ADDED to it
    (accumulated). Otherwise a new row is created with collection/expiry dates.
  * Adjust units: "Add Units" or "Reduce Units" actions.
  * Status is auto-computed on every change:
      units == 0 -> OUT_OF_STOCK (red)
      units <= 5 -> LOW_STOCK    (amber)
      units >  5 -> AVAILABLE    (green)
      EXPIRED status also exists for expired stock shown by the UI.
  * Fulfilling a request deducts units from the bank's inventory.
  * Every add/reduce action writes an InventoryHistory row (audit trail):
    blood_bank_id, blood_group, action (Added/Reduced), units, created_at.
  * Public endpoint /api/inventory/blood-bank/<id> lets anyone see a bank's
    stock (used by map popups) without logging in.
  * Search by blood group and filter by status are provided.

------------------------------------------------------------------------------
5.6 NOTIFICATION SYSTEM
------------------------------------------------------------------------------
  * Notifications are stored in the DB (notifications table) per user.
  * create_notification() helper adds a row: user_id, title, message,
    notification_type, reference_id.
  * Trigger points:
      - New request created        -> matching donors + all banks + admins
      - Donor accepts              -> patient ("Donation Accepted")
      - Bank accepts               -> patient
      - Bank fulfills              -> patient ("Blood Request Fulfilled")
      - Patient verifies donation  -> donor ("Donation Verified")
      - Patient marks fulfilled    -> donors + self
      - Patient marks not fulfilled-> donors
      - Admin verifies/rejects donation -> donor
      - Bank approved/rejected     -> bank ("Blood Bank Approved/Rejected")
      - User blocked/unblocked     -> user ("Account Blocked/Unblocked")
  * Frontend: bell icon with unread badge in the header; dropdown panel;
    polling every 15 seconds; "mark all read". A full Notifications page too.

------------------------------------------------------------------------------
5.7 BLOOD BANK MANAGEMENT & ADMIN APPROVAL
------------------------------------------------------------------------------
  * Blood bank registers via /api/blood-bank/register (needs an existing
    account with role blood_bank). Requires: facility_name, license_id,
    contact_person, address, operating_hours, website, available_24x7.
  * Coordinates: if lat/lng provided they are used; otherwise the address is
    geocoded via OpenStreetMap Nominatim automatically.
  * Status lifecycle: pending -> approved | rejected.
  * Admin approves (with a reason) -> bank gets a notification; if the bank had
    no coordinates yet they are geocoded at approval time.
  * Admin rejects (with a reason) -> bank status = rejected and login is
    blocked; the rejection reason is stored and shown at login.
  * License PDF uploads are saved to /Backend/uploads/licenses with a UUID
    filename (secure_filename + allowed extensions pdf/png/jpg/jpeg).
  * Every approve/reject is logged in blood_bank_admin_actions (audit trail).

------------------------------------------------------------------------------
5.8 CAMP SYSTEM (blood donation camps)
------------------------------------------------------------------------------
  * Only approved blood banks can create camps: title, description, date, time,
    venue, address, latitude/longitude (optional - can be picked on the map).
  * Public endpoints list all / upcoming / current camps (no auth).
  * Banks manage their own camps (my-camps, update, delete).
  * Camps with coordinates appear on the public map.
  * Camps are informational - donors just show up (no sign-up feature).

------------------------------------------------------------------------------
5.9 MAP SYSTEM (Leaflet + OpenStreetMap)
------------------------------------------------------------------------------
  * BloodMap.jsx is a reusable enhanced map:
      - Multiple marker types/colors: banks, donors, hospitals, emergency
        locations, user location.
      - Search by city / facility / address text + filter by blood group.
      - Geolocation "Find my location" button (browser geolocation API).
      - Distance from user to each bank (km/m) shown in popups.
      - "Navigate" button opens Google Maps directions.
      - Inventory lazy-loaded when a bank marker popup is clicked (uses the
        public inventory endpoint).
      - Color-coded legend.
  * Map data APIs: /api/map/blood-banks (public + registered banks with
    coordinates, searchable), /api/map/registered-blood-banks,
    /api/map/camps (upcoming camps with coords).
  * Backend geocoding (Nominatim) powers address -> coordinates.

------------------------------------------------------------------------------
5.10 PUBLIC BLOOD BANK DIRECTORY (eRaktKosh data)
------------------------------------------------------------------------------
  * A public_blood_banks table holds blood bank data imported from eRaktKosh
    (Indian government blood bank dataset) - name, address, phone, facility,
    hospital type, city, state/district codes, lat/lng.
  * Endpoints: list (with state/district/search filters), search by name/city
    (combines public + registered banks), random (half public + half approved
    registered banks, shuffled) - used on the landing page.
  * Registered (approved) blood banks are merged into the same directory so
    users see both government data and our own registered banks.

------------------------------------------------------------------------------
5.11 CONTACT US SYSTEM
------------------------------------------------------------------------------
  * Public form POST /api/contact/send (name, email, phone, subject, message >=
    10 chars). Validated server-side. Saved to contact_messages.
  * Admin inbox GET /api/contact/messages with pagination, unread-first
    ordering, unread_count badge; mark-as-read and delete actions.
  * Used as the appeal channel for blocked/rejected users (messages tell them
    to contact via the Contact page to request an unlock).

------------------------------------------------------------------------------
5.12 UNIFIED DASHBOARD (DUAL-ROLE USERS)
------------------------------------------------------------------------------
  * Since normal registration creates "donor,patient", users get one
    UnifiedDashboard with role toggle tabs.
  * GET /api/user/dashboard returns stats for every role the user has in one
    response (donor stats + patient stats).
  * The same route group also exposes donor/patient profile, screening, and
    donor-search endpoints under /api/user/* for these dual-role users.

------------------------------------------------------------------------------
5.13 DASHBOARD STATS (per role)
------------------------------------------------------------------------------
  * Donor dashboard: total / verified / pending / cancelled donations,
    availability, blood group.
  * Patient dashboard: total / active / completed requests, total units
    requested, total units received.
  * Blood bank dashboard: verification status, total / active / completed
    requests, total units requested, total units fulfilled.
  * Admin dashboard: total users, donors, patients, banks, active/completed
    requests, pending banks, verified/pending donations.
  * Frontend auto-refreshes dashboards every 30 seconds and notifications
    every 15 seconds.

------------------------------------------------------------------------------
5.14 LANDING PAGE & PUBLIC PAGES
------------------------------------------------------------------------------
  * Landing: animated hero (SVG blood drop + particle effects), live urgent
    request counter, top 7 urgent requests (from /api/public/requests/top),
    features grid, testimonials, FAQ accordion.
  * Education: blood group compatibility chart, myths vs facts, health tips,
    eligibility criteria, FAQ.
  * About / Contact / Camps / MapPage / PublicBloodBanks are all public pages.
  * NotFound (404) and Unauthorized (403) pages for bad routes.

------------------------------------------------------------------------------
5.15 FILE UPLOAD (doctor notes)
------------------------------------------------------------------------------
  * Patients can upload a doctor's note (PDF/PNG/JPG/JPEG, max 5 MB via
    MAX_CONTENT_LENGTH). Files are saved to /Backend/uploads/doctor_notes with
    a UUID name. Replacing the note resets verification status to pending.
  * Used by /api/patient/register and /api/patient/profile (multipart form).

------------------------------------------------------------------------------
5.16 ERROR HANDLING & SECURITY PRACTICES
------------------------------------------------------------------------------
  * Global error handlers: 500 handler and a catch-all handler return JSON
    instead of HTML; stack traces are printed server-side.
  * Vague auth errors ("Credentials not matched") so attackers can't tell which
    emails/phones exist.
  * Passwords always hashed (Werkzeug PBKDF2).
  * Phone normalization + validation before storage.
  * Role checks on both frontend (RoleBasedRoute) and backend (@role_required).
  * Ownership checks on every resource (only the creator can update/cancel).
  * Uploaded file names are sanitized with secure_filename + UUID.
  * CORS restricted to the frontend origin.

================================================================================
6. FLOW OF THE PROJECT (end-to-end)
================================================================================

------------------------------------------------------------------------------
6.1 FIRST RUN / BOOTSTRAP FLOW
------------------------------------------------------------------------------
  1. python run.py -> create_app() runs.
  2. Config is loaded from .env (DB URL, secrets, Twilio keys).
  3. db and jwt are initialized.
  4. All 16 blueprints are registered.
  5. db.create_all() creates any missing tables (SQLite file created).
  6. Safety ALTER TABLE statements add columns (license_id, is_active,
     phone_verified) to existing databases (migration for old DBs).
  7. seed_admin_users() creates two admin accounts if they don't exist:
       iamadmin@gmail.com / password
       vinay@gmail.com   / password2

------------------------------------------------------------------------------
6.2 REGISTRATION + PHONE OTP FLOW
------------------------------------------------------------------------------
  1. User fills the registration form on Register.jsx.
  2. They first request an OTP (/api/auth/send-otp). Twilio sends an SMS.
  3. User enters the code in OtpVerification.jsx; /api/auth/verify-otp checks it.
  4. User completes registration (POST /api/auth/register). A user row is
     created with hashed password; donor/patient profiles created; role string
     set. Tokens (access + refresh) returned.
  5. If the phone was OTP-verified during this session, phone_verified is set.
  6. Frontend saves tokens (authStorage.js) and redirects to the dashboard.

  Blood bank registration is separate: after the account is created with the
  blood_bank role, the BloodBankRegister page submits /api/blood-bank/register
  with facility details + license. The bank stays "pending" until an admin
  approves it.

------------------------------------------------------------------------------
6.3 LOGIN + TOKEN FLOW
------------------------------------------------------------------------------
  1. Login.jsx submits identifier (email/phone) + password.
  2. login_user(): finds user, verifies password hash, checks is_active,
     phone_verified, and blood-bank rejected status. Issues tokens.
  3. Frontend stores tokens and sets the axios auth header.
  4. Every API call goes through the interceptor which attaches the token.
  5. On 401 the interceptor uses the refresh token to mint a new access token
     and retries; on success the UI continues seamlessly.

------------------------------------------------------------------------------
6.4 BLOOD REQUEST LIFECYCLE FLOW (patient -> donors -> verify)
------------------------------------------------------------------------------
  1. Patient creates a request (EmergencyRequest.jsx or dashboard).
  2. Backend validates, saves, and broadcasts notifications to matching donors,
     all banks, all admins.
  3. Matching donors see the request in their open-requests list; they click
     Accept -> screening modal -> POST /api/donations/accept/<id>.
  4. Patient gets a notification; the request shows "Responded".
  5. Patient can see the list of accepted donors (name, group, phone, city).
  6. Donation happens offline (at the hospital/camp).
  7. Patient either:
       - verifies each donor individually with unit counts
         (/api/donations/<id>/fulfill), or
       - marks the whole request Fulfilled / Not Fulfilled
         (/api/blood-request/<id>/patient-update).
  8. Verified donations update donor last_donation_date; when fulfilled_units
     reach the required units the request becomes COMPLETED and everyone is
     notified.

  Alternative: a blood bank fulfills the request from its inventory directly
  (/api/blood-bank/fulfill-request/<id>) -> stock reduced, request COMPLETED.

------------------------------------------------------------------------------
6.5 INVENTORY FLOW (blood bank)
------------------------------------------------------------------------------
  1. Bank logs in (must be approved).
  2. Bank adds units for a blood group (POST /api/inventory/ or /adjust).
  3. Backend accumulates units, recomputes status, writes an InventoryHistory
     row.
  4. Dashboard shows stock per group, low-stock/expiry alerts (30s refresh).
  5. When fulfilling a request, stock is deducted automatically.

------------------------------------------------------------------------------
6.6 ADMIN FLOW
------------------------------------------------------------------------------
  1. Admin logs in (seeded account).
  2. Sees dashboard stats and unread notification badge.
  3. Approves/rejects pending blood banks (with reason) -> banks are notified.
  4. Verifies/rejects donations -> verified donations add stock to the bank's
     inventory.
  5. Blocks/unblocks users (with reason, audit trail) -> affected users get
     notifications and lose access.
  6. Completes requests, reviews contact messages, views all camps.

------------------------------------------------------------------------------
6.7 REQUEST -> NOTIFICATION -> ACTION MAP (who gets told when)
------------------------------------------------------------------------------
  Event                        Recipients                Notification type
  ---------------------------  ------------------------  --------------------
  Request created              matching donors + banks  blood_request
                               + admins
  Donor accepted               patient                   donation_acceptance
  Bank accepted                patient                   donation_acceptance
  Bank fulfilled               patient                   blood_request_completed
  Patient verified donation    donor                     donation_verified
  Patient request fulfilled    donors + self             donation_verified /
                                                         blood_request_completed
  Patient request not fulfilled donors                    donation_cancelled
  Admin verified donation      donor                     donation_verified
  Admin rejected donation      donor                     donation_rejected
  Bank approved / rejected     bank                      blood_bank_approval /
                                                         blood_bank_rejection
  User blocked / unblocked     user                      account_blocked /
                                                         account_unblocked

10. IMPORTANT DESIGN DECISIONS & SECURITY
================================================================================

  - JWT instead of Flask-Login: stateless auth, works for tabs + future mobile
    apps. Access token short-lived (30 min) + refresh token long-lived (30 days)
    with automatic silent refresh on the frontend.
  - Phone-first accounts: phone is unique + OTP-verified via Twilio; email
    optional for donors/patients but required for banks/admins.
  - Comma-separated role string enables dual-role users without schema changes;
    @role_required checks membership.
  - Notifications are database-backed (not email/SMS) so all in-app activity is
    visible and auditable.
  - Screening enforced server-side: a donor cannot accept a request without a
    passed screening and a 56-day gap, even if the client is tampered with.
  - Inventory status is always derived from units (0/<=5/>5) so it can't drift.
  - Audit tables (user_admin_actions, blood_bank_admin_actions,
    inventory_history) record WHO did WHAT and WHEN with a reason.
  - Ownership checks everywhere: users can only modify their own resources;
    admins bypass ownership but never role restrictions.
  - Vague auth error messages prevent account enumeration.
  - All uploaded files renamed to UUIDs; extensions whitelisted; size capped.
  - CORS is limited to the frontend origin only.
  - Global exception handlers return clean JSON for 5xx and HTTP exceptions.

11. HOW TO RUN THE PROJECT
================================================================================

REQUIREMENTS:
  - Python 3.x
  - Node.js 18+

STEP 1 - Backend:
    cd Backend
    pip install -r requirements.txt
    # optional: create/edit .env with SECRET_KEY, JWT_SECRET_KEY,
    #           DATABASE_URL, TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN,
    #           TWILIO_VERIFY_SERVICE_SID
    python run.py
  -> API at http://127.0.0.1:5000
  -> Two admins auto-created on first run:
        iamadmin@gmail.com / password
        vinay@gmail.com   / password2

STEP 2 - Frontend:
    cd frontend
    npm install
    npm run dev
  -> App at http://localhost:5173

STEP 3 - Use it:
    1. Register a normal account (donor+patient) and verify the phone OTP.
       (If Twilio credentials are not configured, OTP sending will fail - for a
       local demo you may also add a test/admin user via seed_test_users.py.)
    2. Login and explore the donor/patient unified dashboard.
    3. Register a blood bank account and facility; approve it from the admin
       account; then manage inventory from the bank dashboard.
    4. Raise a request as a patient, accept it as a donor (after screening),
       then verify fulfillment as the patient.

  TIP: The frontend base URL defaults to http://127.0.0.1:5000/api; override
  with VITE_API_BASE_URL if your backend runs elsewhere.
